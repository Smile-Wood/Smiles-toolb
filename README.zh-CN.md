# Smile's toolb

[English](README.md)

Fabric 模组（Minecraft 1.20.1 ~ 26.2，**一个 jar 通用**），只依赖前置库 `Smile's Lib Box`。当前功能：**把 Minecraft 自带讲述人的音色替换为系统语音**。

音色有两个来源，可在配置界面切换：

- **本地**：OneCore 语音库与传统 SAPI5 桌面音色，纯离线合成；
- **在线**：Microsoft Edge 的神经语音（Xiaoxiao、Yunxi 等），走云端合成，需要联网。

## 工作原理

| 层 | 说明 |
| --- | --- |
| 接入点 | `@Mixin(com.mojang.text2speech.Narrator.class)` 注入静态工厂 `getNarrator()`，在返回时把原版实现包装为 `SystemNarrator` |
| 发声 | `SystemNarrator` 只负责清洗文本 + 转发；原版的“关闭 / 全部 / 聊天 / 系统”状态机、聊天朗读、界面朗读逻辑全部保持原样 |
| 本地合成 | JVM 内既没有 WinRT 绑定也没有 SAPI 绑定，因此由一个常驻子进程同时驱动两套本地引擎：**OneCore**（`Windows.Media.SpeechSynthesis`）与 **SAPI5**（`System.Speech`），音频经 `SoundPlayer` 播放 |
| 在线合成 | Edge 的 read-aloud 服务只接受 WebSocket、只返回 MP3：协议与 `Sec-MS-GEC` 令牌由 JVM 侧实现（`java.net.http.WebSocket`），长连接复用；MP3 落盘后交给同一个子进程用 WinRT `MediaPlayer` 播放，`STOP` 能同时停掉两条链路 |
| 配置 | 界面是一份**预设**（`SmileToolbConfig`，只声明页、行、取值范围与读写回调），渲染由前置库 `smile_libbox.api.ui.ConfigScreen` 负责：页签、开关、滑块、重置键全部是原版 widget，材质与悬停态和游戏自带界面一致。真值仍存在 `config/smile_toolb/tts.json` |

失败降级：引擎未就绪、被关闭或合成报错时，一律回退到被包装的原版讲述人，不会出现“静默”。

## 热重载

保存配置即生效，**不需要重启游戏**：

- 音色、语速、音量、单条字符上限：下一条朗读立即使用新值；
- 总开关：开启时自动拉起辅助进程，关闭时后台停掉；
- 更换音色后会自动用新音色试听一句，也可随时按 **F9** 试听；
- “启动时自动开启讲述人”打开后立即把原版讲述人模式切到“全部”；
- 引擎启动失败时，再次保存配置会立刻重试；辅助进程意外退出也会在下次朗读时自动拉起。

## 使用

1. 本模组只有**一个 jar**（`smile_toolb-1.0.4.jar`，1.20.1 ~ 26.2 通用）。
   还要一个前置：**Smile's Lib Box**（装与目标游戏版本匹配的那个 jar）。界面不需要任何
   第三方 GUI 库；Mod Menu 只是可选的入口，装上后模组列表里会多一个「配置」按钮。
2. 游戏内按 **F8** 打开配置界面，**F9** 试听当前音色，或在“按键设置 → Smile's toolb”中改键。
3. 原版讲述人默认是关闭的，按 **Ctrl + B** 切换，或在配置中开启“启动时自动开启讲述人”。
4. 音色列表列出两套引擎的并集，与 Windows *辅助功能 → 讲述人* 里的“选择语音”列表基本一致。
5. 配置界面标题为 **Smile's toolb 配置**，顶部是一排页签按钮（当前页置灰），共两页：
   - **讲述人**：总开关与启动行为、语速与音量、单条字符上限；页面底部是本模组自己加的两颗按钮
     「音色：<当前音色>」与「试听」——音色是运行时枚举出来的动态数据，不适合做成普通配置项；
   - **杂项**：「使用旧版经验条动作」「高级状态条控制」（1.21.9+ 或装有 VanillaBackport 时才出现，
     由运行时探测 `BarFeatureDetector` 过滤，1.20.1 直接隐藏）、「保留聊天框内容」与「草稿保留时长」、
     「召唤数量」、「退出按键映射」与退出按键列表，以及底部的「召唤假人 / 删除假人（N）」
     （服务端有 Carpet 的 `/player` 命令时才可用；挂批量任务时两颗按钮一起禁用，
     下面一行红字「批量执行中，剩余 N 条命令」）。
6. 点「音色」按钮进入独立的**音色选择界面**：顶部搜索框、全部 / 本地 / 在线三个筛选、可滚动列表
   （每行右侧标注 OneCore / SAPI5 / 在线 与语言）、底部「在线音色开关」「试听」「完成」。
   点击任意一行即切换并立刻试听，选择同时写盘；`↑` / `↓` 换音色，回车重听。
   这样音色再多也不会把配置页撑长。
7. 「在线音色」开关位于音色选择界面左下角，控制是否把 Edge 语音并入列表，列表中带“在线”
   标记。在线音色按游戏语言筛选（中文环境下为 14 个），避免把服务端三百多个音色全塞进列表。

## 状态条控制（杂项，1.21.9+ / VanillaBackport）

1.21.9 起，快捷栏上方那一条改成了「上下文条」：只要附近有带路径点的队友
（`WaypointManager#hasWaypoints()` 为真），显示的就是**玩家追踪条**（locator bar），
经验条被挤掉；只有刚获得经验后的 100 tick（5 秒）里才临时切回经验条。而骑乘可跳跃坐骑时
原版又是无条件的跳跃条，不按跳跃也一直挂着。「和队友一起玩就看不到经验」正是这套规则造成的。

杂项里有两条开关，后者是前者的加强版：

- **使用旧版经验条动作**（默认开）：把追踪条压掉，这一条固定是经验条，其余保持原版
  （骑乘时仍然是跳跃条）。相当于回到 1.21.8 及以前的表现。
- **高级状态条控制**（默认关，需上一项开启）：按场景自动切换——
  - 默认：经验条；
  - 按住**玩家列表键**（默认 Tab）且附近有队友路径点：定位条（没有路径点时定位条是空的，
    所以保持经验条）；
  - 骑乘可跳跃坐骑时按住**跳跃键**：蓄力条；松开后继续保留 **2.5 秒**，再切回经验条。

低于 1.21.9 且没装 VanillaBackport 的版本没有上下文条，这两个开关都不显示；配置文件里
仍保留字段，在高低版本之间来回换不会丢设置。1.20.1 装了 VanillaBackport 时的差异见下一节。

门控只看 `GameVersion.atLeast("1.21.9")`：26.2 这类年份版本按语义版本比较，
`26 > 1` 成立，所以高版本直接判 `VANILLA`。实机结果：26.2 配置界面
12 行 / 4 个开关、两个追踪条开关可见；1.20.1 为 9 行 / 2 个开关、追踪条开关隐藏，
其它配置项齐全且界面正常打开。两边都进主界面、零异常；日志对应
`状态条特性检测` 与 `配置界面自检` 两行，详见 `VERIFY.md` 第 0 节。

实现方式：注入 `Gui#nextContextualInfoState()` 的 RETURN，直接替换最终状态。之所以不再改
`willPrioritizeExperienceInfo()`，是因为原版没有路径点时走的是 `if (jumpable) return
JUMPABLE_VEHICLE` 这条无条件分支，那个开关根本不会被求值，想让「骑乘不按跳跃时回到经验条」
只能改返回值。`Gui.ContextualInfo` 是包私有枚举，源码里引用不到它的类型，因此用 `Object`
接收返回值，由 `ContextualBarController` 反射取四个常量并缓存（正式环境常量名是 intermediary
名，认不出来时按声明顺序 EMPTY / EXPERIENCE / LOCATOR / JUMPABLE_VEHICLE 摆放）；2.5 秒窗口
由 `ClientTickEvents.END_CLIENT_TICK` 跟踪跳跃键的按下 / 松开。这段注入由前置库
按游戏版本分别编译并由 `LibBoxMixinPlugin` 门控，低版本不启用该 mixin。

### 低版本 + 定位条 backport 模组

低版本（1.20.1 ~ 1.21.8）没有原版上下文条，但整合包里常见把定位条搬到低版本的模组。
`BarFeatureDetector` 在启动时按可靠度判断这两个开关要不要出现：

1. 游戏版本 ≥ 1.21.9：原版上下文条，`ForceExperienceBarMixin` 接管；
2. **VanillaBackport（1.20.1，id `vanillabackport`）**：已针对性适配，见下一节；
3. 低版本但 `Gui` 里存在「返回那个四状态枚举」的方法：判定为别的模组把原版上下文条 API
   一起搬了过来（按返回类型找，不依赖方法名，尚未适配）；
4. 否则按已加载模组的 id / 名称关键词（`locator` / `waypoint`，外加已知的 `wayfarer`）推断。

命中第 3、4 类时两个开关同样会列在「杂项」里，并附一行兼容性说明。**边界要说清楚**：
这些模组的条是它们自己绘制的，不经过原版 `Gui`；低版本对应的库 jar 不会启用
原版上下文条 mixin。因此开关会保留（配置值跨版本不丢），但不会改变第三方定位条的
显示，需要在对应模组自己的设置里调整。不同模组之间没有通用接口，只能逐个适配。

#### VanillaBackport 1.2.2（针对性适配）

这个模组的 id 和名字里都不含 `locator` / `waypoint`，关键词推断抓不到它；现在按
mod id + `LocatorBarRenderer` 类是否存在精确识别（日志关键字 `检测到 VanillaBackport 定位条`）。

它的定位条是**叠加覆盖式**的：经验条 / 跳跃条照旧绘制，只是
`LocatorBarRenderer#shouldSkipRendering()` 返回 false 时，会在同一位置再盖一层定位条背景
和路径点图标。这个方法同时被 `renderBackground()` 与 `renderWaypoints()` 调用，是唯一总闸门。

- `VanillaBackportBarMixin` 是软目标 mixin（`@Mixin(targets = ..., remap = false)` +
  `require = 0`），注入该方法的 RETURN 改写返回值，背景与图标一起受控；
- 它放在独立的 `smile_toolb.backport.mixins.json`（`required: false`），由
  `BackportMixinPlugin` 按 `vanillabackport` 是否加载门控。没装这个模组时，这个
  mixin 类根本不会被解析，不会和别的模组抢同一个方法；
- `BackportBridge` 反射读取 `ClientWaypointManager#hasWaypoints()` 和
  `ClientConfig#enableLocatorBar`，保证「没有路径点不画空条」「尊重 backport 自己的总开关」。
  反射失败一律退回「不干预」，不会让游戏崩。

两个开关在 1.20.1 上生效：只开「使用旧版经验条动作」时恒跳过定位条，这一条固定显示经验条；
再开「高级状态条控制」时默认经验条、按住 Tab 显示定位条、骑乘按住跳跃让蓄力条露出且松手后
2.5 秒内继续保持。

**已知差异**：1.20.1 原版 `Gui#render` 在 `jumpableVehicle() != null` 时无条件调用
`renderJumpMeter`，所以骑乘但不按跳跃时显示的是（空的）跳跃条，无法像 1.21.9+ 那样切回
经验条。这是原版结构决定的，本模组没有强行改写它。

**配置冲突**：若 backport 自己的 `locator_display_info_bar` 被打开，它会在有经验 / 骑乘时
提前跳过定位条背景，导致高级模式下按住 Tab 只剩图标、没有条。配置界面会检测到并提示关闭。

## 保留聊天框内容（杂项）

默认开启。关闭聊天框后再打开、退出服务器后短时间内重进、换客户端顶号重启，都会回填
上一次**未发送**的输入；消息一旦发送，草稿立刻清除。

- 入口：配置界面 → **杂项** → 「保留聊天框内容」开关与「草稿保留时长」
  （60~3600 秒，默认 600 / 10 分钟），下一行显示当前缓存的草稿条数。
- **判定只按连接地址**：key 是玩家填写的服务器地址（`ServerData.ip`），大小写不敏感，
  带不带默认端口 `:25565` 视为同一台；不同服务器互不干扰，与玩家名、世界名、客户端实例
  无关。地址由库侧 `Ui.serverAddress()` 提供，被踢 / 断线时它会短期记住最后一次地址，
  避免草稿在那一刻存到错误的 key。
- 草稿文件在**用户主目录** `.smile_toolb/chat-drafts.json`，不在 `.minecraft/config/`——
  不同游戏目录 / 不同启动器的客户端读同一份文件，这才是「换客户端顶号」能恢复的原因。
  写盘用临时文件原子替换，草稿清空后文件自动删除，超时条目在每次读写时清理。
- 注入点由库按版本各编一份（`ChatScreen#init` 回填、`onClose` 捕获、`removed` 兜底、
  `handleChatInput` 清空），本模组只注册纯 Java 回调，这一侧仍是零 MC 引用。
- **在 `onClose` 的 HEAD 抓文本**，不是等 `removed()`：1.21.x 起原版会在关闭时先处理
  自己的会话内草稿，可能顺手清空输入框，等到 `removed()` 只剩空串。一次打开只抓一次
  （`onClose` 抓过之后 `removed` 不再插手），并额外挡住「保存后 400ms 内的清空」，
  免得重复回调把刚存下的草稿抹掉。
- **「发送」不等于「关闭」**：原版 `handleChatInput` 只发包、不清空 `EditBox`，紧接着
  `keyPressed` 才 `setScreen(null)`，于是 `removed()` 里读到的仍是刚发出去的那条。
  库侧因此在提交时记下原文，`removed()` 发现内容没变就当作「发送后关闭」不落盘
  （1.21.x 原版用 `exitReason == DONE` 做同一件事，1.20.x 没有这个字段）。
- 原版高版本自带会话内草稿，本功能只在输入框为空时回填，不覆盖原版刚保存的内容。

逐场景的人工验证清单见 `VERIFY.md` 第 7 节。

## 战斗辅助（战斗辅助页）

两个功能共用一套**护甲锁状态机**（`smile_toolb.client.combat.ArmorLock`）：

| 状态 | 含义 |
| --- | --- |
| `IDLE` | 地形安全，完全不干预 |
| `GUARDED` | 地形危险，正在守卫 |
| `LOCKED` | 重锤流程占用，退出由流程决定 |

锁定时，「往胸甲槽放鞘翅」的容器操作在**发包前**就被丢掉（走库的 `Packets` 黑箱拦截，
不碰任何 MC 包类型）；万一有模组绕过发包入口直接改栏位，每 tick 的复查会把它换回来。
玩家自己开着背包换鞘翅时一律放行——这就是「不是玩家手动操作」的判定依据。

守卫态下有三件事**绝对不碰**胸甲槽：

- **正在滑翔**：鞘翅就是此刻唯一的依靠，拆掉等于让人摔死（滑翔中「只守不拆」：状态留在
  `GUARDED` 让拦包继续生效，只是不跑换回逻辑）；
- **真的在坠落 / 已经在空中**（离落脚面 ≥ 1.75 格，比普通跳跃顶点 1.25 高）：这时
  一枚自动换上的鞘翅往往是最后的自救手段，落地站稳了再收拾。**被击退、被怪弹飞、
  被爆炸抛起来**的瞬间就是靠这一条让路的——早先只在「超过 3 格」时才让位，
  而头顶有天花板的地方（净空 ≤ 3）根本不看高度、一路锁到落地，
  于是「被弹飞却切不出鞘翅」正好卡在离地两三格那一段；
- **进守卫时就穿着鞘翅**：那是玩家自己的装备，需求只禁止「自动切换」，不拆家。
  只有「守卫期间被自动换上的鞘翅」才会被换回护甲。

判据不是 `onGround`，而是扫描结果里的 `drop`（脚部离落脚面多高）+ 净空：

| 情形 | 结论 |
| --- | --- |
| 离落脚面 > 3 格（彻底离开这一格） | 让位 |
| 离落脚面 ≥ 1.75 格（已在空中，含被弹飞） | 让位——鞘翅是自救手段 |
| 净空 ≤ 3 + 贴地（离地 < 1.75） | 守卫，跑跳也拦 |
| 露天窄道 + 真的站在面上（离地 ≤ 0.6） | 守卫 |
| 露天窄道 + 已经起跳（离地 > 0.6） | 让位——那是「想飞」不是「违规」 |

最后两行是「刚起飞就被拽下来」的修复：露天窄道上玩家起跳想滑翔，脚才离地一两格，
若照样把刚穿上的鞘翅扒掉，体感就是把意图判成违规，人直接被拉下来。

1.75 这个门槛的来源：普通跳跃顶点 1.25 格，低于它就一定是「跳起来的那一刻」，
那时穿上的鞘翅只会撞头，正是窄道保护要挡的；高过它说明人是被外力抛起来的，
穿着鞘翅不一定能飞，但不穿一定没机会。被弹飞后落地站稳，守卫照旧接管。
代价是这时别的模组有机会把鞘翅塞进来，不过落地后 `baselineElytra` 仍是 false，
`enforce()` 会把它换回护甲。

地形基准也跟着修了：雪层 / 地毯 / 台阶的碰撞高度不到一格，脚部坐标会落在那格里。
改前把它当成天花板，净空算成 0 → 平地上站着也判危险（实测日志里每 tick 都在
「开始守卫 / 停止守卫」之间抖），一起跳就把自动换上的鞘翅扒掉。现在这种方块按「地面」处理。

**净空改成了连续高度**（`World.blockHeight()`：地毯 0.0625、雪层 0.125、台阶 0.5、
满格 1.0）。早先按「整格 + `isSolid`」计数，地毯既算地面又算天花板：站在双地毯上，
脚部坐标被逐格抬到 46 / 47 格，四格高的走廊被量成两格甚至一格 —— 日志里
`净空=1，离地=0.1` 就是站着不动时的读数，接着就是误守卫、自动换上的鞘翅被扒。
现在落脚面取「碰撞高度累加的顶面」（双地毯 = 45.0625），天花板只认满格方块，
四格高走廊读 3.9 → 安全，三格高读 2.9 → 照常守卫。

地形扫描**每 tick** 一次（早先 5 tick 一次跟不上跑跳节奏，人已进门、状态还是「安全」）。
最贵的平台检测只在「净空够 + 宽度 ≤ 3」时才跑，也就是唯一可能左右结论的场合。

换回的目标是背包里**最强的那件**护甲：附魔条数优先，其次耐久上限
（皮革 81 / 金 113 / 铁与锁链 241 / 钻石 529 / 下界合金 592）。

### 鞘翅安全守卫

判定在 `smile_toolb.client.combat.Terrain`，两条危险条件满足一条就守：

| 条件 | 含义 |
| --- | --- |
| 净空 ≤ 3 格 | 落脚面到天花板底面的连续高度，穿鞘翅会撞头（薄方块只扣各自的碰撞高度） |
| 露天 + 落脚宽 ≤ 3 + 两侧下方 5 格内无 5×5 平台 | 摔下去没有落脚点 |

**1×1 竖井是例外**：宽 1、四面夹墙、往上至少 4 格的竖直通道照样判安全——那是可以顺着
爬升的井，不是「飞出去就掉」的窄道。宽 1 的两种地形靠**四面有没有墙**分开：半空单方块
小路四面临空 → 危险；竖井四面是墙 → 允许起飞。三格深、四格深的 1×1 小坑仍按净空守卫。

两条都量在**脚下最近的那个面**（往下 12 格内找第一个固体方块）而不是脚部坐标本身：
人一跳起来脚下就是空气，按脚部高度量宽度会恒等于 1，平地起跳也会被当成窄道。
12 格内找不到地面（高空）则当作悬空，宽度规则不适用。

四个基准场景由 `python tools/selftest-terrain/run.py` 自检（纯 Java，不加载游戏）：

| 场景 | 净空 | 宽 | 露天 | 结果 |
| --- | --- | --- | --- | --- |
| 半空单方块小路 | 64 | 1 | 是 | 危险 |
| 地下 2 格高 1 格宽 | 2 | 1 | 否 | 危险 |
| 地下 3×3 通道 | 3 | 3 | 否 | 危险 |
| 地下 4×4 通道 | 4 | 4 | 否 | 安全 |
| 露天草地上起跳 1.5 格 | 64 | 17 | 是 | 安全 |
| 单方块小路上方 3 格 | 64 | 1 | 是 | 危险 |
| 高空悬停 20 格 | 64 | 8 | 是 | 安全 |
| 双地毯 4 格高走廊 | 3.9 | 3 | 否 | 安全 |
| 双地毯 3 格高走廊 | 2.9 | 3 | 否 | 危险 |
| 1×1 竖井（四面是墙） | 64 | 1 | 是 | 安全 |
| 1×1 三格深坑（封顶） | 3 | 1 | 否 | 危险 |
| 两面墙的壁龛 | 64 | 1 | 是 | 危险 |

配置界面底栏常驻一行 `护甲锁：守卫中|净空=2.0 宽=1 露天=否 平台=有 危险=是`，
状态翻转时日志也会打一行 `护甲锁：`。

### 守卫中被模组塞了烟花

窄道里打怪时手里没了武器，攻击直接断掉——干这事的典型是 tweakeroo 的「自动切换烟花火箭」：
它挂在起飞判定上，把背包里最好的火箭**换进当前手上那一格**。

判定（`combat/HandSwap`，纯 Java）只认一种形态：

| 两 tick 之间发生了什么 | 谁干的 | 处理 |
| --- | --- | --- |
| 选中槽没变，槽里的东西变成烟花 | 模组把火箭换进了这一格 | 换回原来的武器 |
| 选中槽变了（切到放着烟花的那格） | 玩家滚轮 / 按 1~9 | 不管 |

玩家没有任何按键能在**不改选中槽**的前提下换掉格子里的东西，所以这个差异足以把
「模组的自动切换」和「玩家自己的选择」分开——这就是「被模组切烟花了就换回去」与
「不许烟花出现在手里」的区别。

另外四种情况也不动手：**滑翔中**（火箭就是加速手段）、**开着背包 / 容器**（自己的鼠标）、
**环境安全**（不干预）、**已经离开危险格子**（在露天窄道上起跳准备飞，正是要火箭的时候）。

换回走 `World.holdItem(原武器)`：热键栏里有就切槽，只在背包里就发一次容器点击包换过来
（服务端权威，多人服同样有效）。换回后有 10 tick 冷却，不会连发点击包。
日志：`护甲锁：守卫中手里的烟花是别的模组换上的，已换回 minecraft:xxx`。

### 重锤猛击

触发：正在下落（竖直速度 < -0.08，Xaero 那套口径）+ 按住潜行（可关）+ 背包有重锤 +
**离地 / 已坠落 > 1.5 格** + **下方有东西可以砸**。动作：锁甲 → **切重锤**（**优先致密等级最高的那把**，同级时附魔条数多的优先；在热键栏就切槽，
只在背包就用容器点击包换到当前槽）→ 胸甲是鞘翅就换护甲 → 预计落地前 N tick 挥击最近实体
→ 落地解锁 → 无目标时把飞行装备装回去。

**先切锤、再摘鞘翅**这个顺序是有意为之：反过来的话，背包里没锤时会先把鞘翅摘掉——
人已经被拽下来开始掉了，锤又切不出来，等于白摔一次。先切锤，切不出来人还在滑翔。

1.5 格这道门槛是「跳一下也触发」的修复：普通跳跃顶点只有 1.25 格，原版猛击的强化伤害
也要坠落距离 > 1.5 格才成立，低于它挥出去是空挥，却会白锁一次甲、白换一次锤再换回来。
判据取 `max(离地高度, 原版坠落距离)`，刚起跳时两者都是 1.25，都能挡住。

**原地下砸**（默认开，可在页内关掉）——指的是**取消滑翔**，不是把人钉在一条竖直线上：
滑翔中把胸甲槽的鞘翅摘掉（原版「身上没有可用的鞘翅就飞不了」，滑翔当场中止），
人从当前位置往下掉，然后走同一套猛击流程。**速度一点不动**：滑翔的横向动量、WASD
操控全部保留，落点偏了可以自己微调——滑翔的水平速度能到 1 格/tick 以上，所以要按
「竖直落下去」而不是按当前速度找目标。

滑翔中要动手，必须同时满足「**按住潜行键**」「**目标在手长柱里**」「**按住够久**」三条。
「够久」按视角分两档（`combat/GlideDive`，纯 Java 可自检）：

| 视角 | 需要按住 | 为什么 |
| --- | --- | --- |
| 俯视 ≥ 60°（低头盯着落点） | 3 tick | 意图明确，鼠标扫过也不算 |
| 平视 / 抬头 | 8 tick（约 0.4 秒） | 滑翔时 shift 本来就是原版的加速下降，飞过生物按着它是常事；但**不能因为没低头就判成「不想砸」** |

「目标在手长柱里」这一条不接受运动预判：路过的怪、开过来的船能把「预判命中」喂成真，
一旦摘了鞘翅就回不去了。

早先这里只认「俯视 ≥ 60°」，结果平视按着 shift 一次都不触发——按 shift 想下降的人不会
先低头摆姿势。现在平视按住 8 tick 同样算数，低头则 3 tick 就动手。

目标在手长柱间漂移时**计数只回退、不清零**（`GlideDive.decay`）：滑翔的水平速度是
0.4~0.7 格/tick，柱子两侧各手长宽，一次穿越本来就只有十几 tick，中途几 tick 滑出柱外就
把累计清零，8 tick 永远攒不满——这是「按着也还是不下落」的第二个成因。下坠流程里条件
不成立就是真的不成立，直接清零。

按住但还没到时机时，日志每 20 tick 打一行读数，方便区分是卡在视角、柱内还是保持时长：

```
重锤猛击：滑翔中等下砸（目标 手长柱内 minecraft:wolf（4 tick 后落地）；俯仰 12°，需保持 8 tick，已保持 5，离地 6.3 格）
```

摘不下鞘翅（背包里没有别的护甲）时会直接收手并解锁，不会卡在「重锤锁定」状态里。
关掉这个开关后，滑翔中完全不管。日志会打
`重锤猛击：摘下鞘翅，取消滑翔（目标 …）`。

「下方有东西」是两段判定（`combat/SlamTargets`，纯 Java，可脱离游戏自检）：

1. **手长柱**：以玩家为中心、水平半宽 = 手长（默认 3 格，即原版交互距离），从脚下一直
   延伸到当前脚下的地面；柱子里碰到实体碰撞箱就算命中。
2. **运动预判**：两倍手长（6 格）内，把每个实体的速度外推到「你现在立刻落地要几 tick」，
   外推后的位置只要落进「落点 ± 手长」那一段，也算命中——船在水面漂过来、怪走过来、
   和你一起下坠的实体都会因此被算上。

船、盔甲架算实体（它们 `isPickable()`）；掉落物、箭、经验球不算。
手里的手长可以在配置里改成 2~6 格，实际挥击仍受原版 3 格交互距离限制。

原版猛击要求「攻击时玩家仍在下落」，落地那一帧再打就不算，所以要提前挥。这个提前量
**默认按延迟自动算**（`combat/LeadEstimate`，纯 Java，可脱离游戏自检）：

```
lead = clamp(ceil(ping / 100) + 1, 1, 8)     // 自动模式取 max(手动值, 上式)
```

| 往返延迟 | 提前量 | 场景 |
| --- | --- | --- |
| 0 ms | 1 tick（手动值 2 兜底 → 2） | 单人本地 |
| 50 ms | 2 tick | 同城服务器 |
| **200 ms** | **3 tick** | **跨省 / 海外线路** |
| 430 ms | 6 tick | 卫星 / 极端线路 |
| ≥ 700 ms | 8 tick（封顶） | 再往上不再增加 |

推导：往返 `ping` 毫秒 = 单程 `ping/2` 毫秒 = `ping/100` tick，攻击包在路上要飞单程，
向上取整，再加 1 tick 缓冲（客户端预测按 tick 离散、发包落在 tick 边界、服务端对齐自己的 tick）。
不自动时严格按配置里的手动值走；自动时手动值是**下限**，只会被顶高、不会被压低。

两点边界：

- **提前量不是越大越好**。它直接吃掉坠落距离，而坠落距离正是猛击的伤害倍率来源，所以
  上限压在 8 tick。200ms 的 3 tick 大约损失 2 tick 的下落高度，比「整锤不成立」划算得多。
- **它治不了「距离不够」**。高延迟时服务端看到的玩家位置比实际落后，挥击若被判超出手长，
  再早发包也没用——那是手长（`maceSlamReach`）该调的事。

tab 列表里的延迟每秒才刷新一次，读数会在几十毫秒内跳动，所以这里做 1/8 指数平滑；
配置界面底栏右侧会常驻显示 `延迟 200ms（自动 3，实际提前 3 tick）`，日志里也会带上
`提前 N tick，延迟 Mms`，方便对照。

1.20.x 没有重锤，这个功能在那几个版本自然永不触发。

**挥击前会把锤子再捏一次。** 流程开头那次切锤只管「开始下砸」那一刻，落地前这几 tick
里这一格仍可能被别人动：客户端只要把「跳起 + 按住空格」判成起飞，tweakeroo 的
「自动切换烟花火箭」就会把火箭换进当前槽——那一挥就成了拿烟花空挥，猛击不成立，
还白耗一发火箭。所以进入挥击窗口前 2 tick 就开始校验手上：

```
手上不是 minecraft:mace  →  重新切锤（热键栏直接切槽，只在背包则走容器点击包）
                           切回来了：同一 tick 继续判断并挥击
                           没切回来：这一 tick 不打，下一 tick 再说
                           连续 3 次都被抢走：收手，落地时恢复原武器
```

日志对应 `重锤猛击：手上是 minecraft:firework_rocket，重新切重锤（本 tick 已生效）`，
挥击那一行也会带上当时的 `手上 …`，跟着日志就能看出那一锤到底是用什么打的。

收工会把手上换回动手之前的那把（`重锤猛击：把手换回 …`）。换手是容器点击包、要一 tick
才落地，所以落地那一帧没成功的话，接下来 20 tick 里每 tick 再试一次；玩家自己中途换了
别的东西就立刻放手。切不出重锤（背包里找不到 / 服务端拒绝）时直接收手，不用手里那把
去空挥。

「玩家自己换的」与「锤被模组换走的」外观一样，所以流程里一旦发现手上不是锤就记一个标志：
带着这个标志收工，即使手上是烟花也照样换回原武器（判据 `HandSwap.shouldRestore`，
纯 Java 可自检）。这是「落地后人事不知地攥着烟花」那一版问题的修复。

### 砸完被弹飞：无目标就恢复飞行

一次猛击的完整链子是「按住潜行 → 下方有目标 → 切锤 → 换护甲打断滑翔 → 落地猛击」。
但战斗里常见的是**砸完立刻被弹飞**——风暴、爆炸、击退、怪物的弹射技能都会把人抛起来。
那一刻手上是剑、胸甲槽是护甲，飞不起来，只能干看着自己往下掉。

所以收工后留一段 **40 tick（两秒）的观察窗口**：只要满足下面三条，就把飞行装备装回去
（`combat/FlightResume`，纯 Java 可自检）：

| 条件 | 取值 | 为什么 |
| --- | --- | --- |
| 人在空中 | `onGround == false` | 站着穿鞘翅没有意义，窄道保护也正该管着 |
| 离地 ≥ 1.75 格 | 普通跳跃顶点 1.25 | 把「自己跳一下」和「被外力抛起来」分开 |
| 下方没有**要砸**的目标 | 有实体**且**按着潜行才算 | 有目标又在按潜行 = 继续砸；否则 = 想飞 |

装回去的动作分两步（换装走容器点击包，要一 tick 才落地）：

```
本 tick   胸甲槽换回鞘翅      → 日志「重锤猛击：把鞘翅穿回去，恢复飞行」
下一 tick 手上换成烟花火箭    → 日志「重锤猛击：把烟花火箭换到手上，可以继续飞」
```

背包里没有鞘翅时不硬撑：关掉窗口，照常把武器换回来——把人晾在半空、手上还攥着锤子
是最糟的结果。窗口内人一直站在地上（砸完安稳落地）就什么也不做，两秒后自然结束。

**流程中途目标没了也会收工**：甲已经锁了、鞘翅已经摘了、锤也在手上，目标却消失
连续 3 tick（过滤掉走位抖动），这时不会继续锁着往下摔，而是直接收工走上面这套恢复流程。
这就是「无可猛击实体 → 切回鞘翅和烟花火箭」那条规则。

配置界面里是「无目标时恢复飞行」，默认开；关掉就退回「只换回武器」的老行为。

## 快速召唤假人（杂项）

给打试炼（trial chambers）用的一键工具：随机取名召唤一批 Carpet 假人，用完一键删除。

- 入口：配置界面 → **杂项** → 「召唤数量」「假人发送间隔」两个滑块，最底部那一行
  （与「全部重置 / 完成」同一行）放「召唤假人」「删除假人（N）」两颗按钮，批量任务
  进行时按钮右侧红字提示状态。
- 这两颗按钮放在库的**底部那一行**里（`page.bottom`）：宽度由库按文字统一算、
  从左往右自动续排，与系统按钮同行但不会压住它们，**不随中间列表滚动**，
  所以滚到第几行都能直接点。召唤按钮的文字不再带数量 ——
  数量在它上面的滑块里，按钮上再写一遍容易被误读成「点一次就是这个数」。
- **批量任务进行中**：两颗按钮一起置灰（队列里不叠新命令，也不会「刚召唤又删除」），
  同一行右侧红字显示剩余命令条数（`批量执行中，剩余 N 条命令`）；队列发完、记录落盘后自动恢复。
- **数量可调 1~50，默认 20**。滑块是原版控件：点轨道哪一段就跳到哪，按住可以
  左右拖；点右边的数值框可以直接键入数字（第一次键入替换原值），回车确认、Esc 取消。
- **发送间隔可调 1~100 tick，默认 10**（约 2 条/秒）。这是被服务端反刷屏踢过之后的
  可调项：1 tick ≈ 20 条/秒正贴着原版 `TickThrottler` 的令牌桶上限，客户端与服务端
  tick 稍一错开就会瞬间抽干；服务端装了更严的聊天/命令反刷屏时把它调大即可，
  最大 100 tick（5 秒一条）。配置里改完立即对下一条命令生效，不用重进游戏。
- **需要服务端提供 Carpet 的 `/player` 命令**（安装了 Carpet、`commandPlayer` 没关、
  当前玩家有权限）。判断依据是服务端下发给客户端的命令树里有没有 `player` 根节点，
  而不是猜 mod id；拿不到就只显示一行说明，按钮不出现。
- **命令仅发包**：走客户端连接对象的 `sendCommand`，不打开聊天框、不写聊天记录，
  也不会把命令留在输入框里。命令按上面的间隔逐条排队发出，不会一次刷出几十条。
- 名字格式 `bot_` + 4 位小写字母数字（共 8 字符，符合 MC 用户名 3~16 的限制），
  同一批内去重，并避开已记录的名字。
- **删除前先丢物品**：对每个假人先发 `/player <name> drop`（背包物品全部丢出），
  下一 tick 再 `/player <name> kill`（移除假人），避免打试炼捡到的装备跟着假人消失。
- **数量实时同步**：「删除假人（N）」里的 N 不是本地记录，而是每 0.5 秒从服务器的
  在线名单（Tab 列表）里数一遍名字以 `bot_` 开头的玩家。假人被打死、被手动清掉、被别的
  客户端补进来，数字半秒内跟着变；配置界面开着就一直刷新，不用退出重进或重开界面。
- **删除也按这份实时名单**：按钮上的数字和实际发出的命令条数永远一致 —— 不会对空气发
  `kill`，也不会漏掉上一轮留下的假人。归属只认名字前缀（Carpet 的假人在服务端就是个
  普通玩家，没有「谁召唤的」这种标记），所以**别的客户端召唤的 `bot_` 假人也会被一起删掉**，
  公共服请留意。
- **执行中逐条复核**：每发一条命令之前再取一次实时在线名单，名字已经不在的一次性剔掉、
  不占发送间隔 —— 假人中途被打死 / 被别人清掉时，一批 40 条命令不会还傻等到最后一秒；
  全没了就当场收工。名单为空（还没下发完、已经退出）时不动队列，宁可按原样发。
- 召唤记录按**连接地址**镜像在用户主目录 `.smile_toolb/dummies.json`：名单还没下发完
  （刚进服、刚换维度）时用它兜底，换客户端顶号也能删掉上一轮留下的假人，不同服务器
  互不干扰。名单为空时只更新界面数字、不动文件，不会把记录清成空；批量任务进行中也不
  落盘，避免和队列收尾时的写盘互相覆盖。
- `drop` / `kill` 由 Carpet 执行；假人已经不存在时命令会报错，但不影响后续条目。


## 退出按键映射（杂项）

讲述人之外，模组还提供了一个辅助功能：把任意按键（键盘键或鼠标键）映射成「按 Esc」。

- 入口：配置界面 → **杂项** → 「退出按键映射」（按钮上显示开关状态与键名，默认
  「开 · 鼠标按键4」）。
- 默认只绑定**鼠标侧后键**，出厂即启用。`key.mouse.N` 的 N 是「第 N 个鼠标键」：
  侧后键（后退 / XBUTTON1、GLFW button 3）是鼠标按键 4，侧前键（前进 / XBUTTON2、
  GLFW button 4）是鼠标按键 5。个别厂商会把两个物理侧键对调，此时在界面里「添加按键」
  按一次真实侧键就能确认真实编号，再移除不需要的那个。
- 列表可增删：点「添加按键」后直接按下目标键即可录入（键盘键、鼠标侧键 / 中键 / 右键
  都行，鼠标左键留给点击界面，会提示不能绑定），Esc 取消录制，点行尾「移除」删除。
  每次改动立即写入 `tts.json`，不需要回配置页保存。
- 启用后，在任意界面按下列表中的键，等同于按 Esc 关闭当前界面；界面本身不允许 Esc 关闭时
  （例如连接进度界面），自定义按键同样不生效，行为与 Esc 完全一致。
- 实现方式：键盘注入 `Screen#keyPressed`、鼠标注入 `MouseHandler#onPress` 的 HEAD，判据复用
  `shouldCloseOnEsc()`。只影响已打开界面，游戏中不会吞掉按键；录制界面本身跳过注入，
  否则刚录好的侧键会立刻把设置界面自己关掉。若映射的是常用字符键，该键在输入框内也会
  先关闭界面，请避免选择字母 / 数字键。
  （鼠标不能注入 `Screen#mouseClicked`：1.20.1 里它只是 `GuiEventListener` 的接口默认方法，
  `Screen` 没有重写，注入会因找不到目标而在启动时崩。）
- 旧版本配置里的 `exitKeyCodes`（GLFW 键码）会在读取时自动迁移成键名，之后不再写回。

配置与缓存文件位于 `.minecraft/config/smile_toolb/`：

- `tts.json`：模组配置
- `voices.json`：音色列表缓存（本地 + 在线）
- `cache/edge_*.mp3`：在线合成的临时音频，保留最近几条后自动清理
- `narrator_helper.ps1`：辅助脚本，每次启动由模组重新生成（请勿修改，会被覆盖）

## 音色来源与边界

| 音色 | 来源 | 是否可用 |
| --- | --- | --- |
| `Microsoft Huihui / Yaoyao / Kangkang` | OneCore 语音库（`HKLM\SOFTWARE\Microsoft\Speech_OneCore\Voices`） | 可用（WinRT 引擎） |
| `Microsoft Huihui Desktop / Zira Desktop` | SAPI5 语音库（`HKLM\SOFTWARE\Microsoft\Speech\Voices`） | 可用（SAPI 引擎） |
| `Microsoft Xiaoxiao (Natural HD)` 等 | MSIX 语音包 `MicrosoftWindows.Voice.*` | **本地不可用**，见下；在线可用同名神经语音 |
| `Microsoft Xiaoxiao / Yunxi / Xiaoyi …`（在线） | Edge read-aloud 服务 | 可用（联网） |

**关于 Natural HD**：这类语音以“只有数据、没有引擎”的 MSIX 包形式安装
（包内仅有 `hd_am_*` / `hd_device_vocoder_*` 模型文件与 `Tokens.xml`），其神经渲染器
（`NeuralRenderAdapterImpl`）内嵌在 `Narrator.exe` 中，对应的 CLSID `{a12bdfa1-...}`
**没有注册到系统 COM**，令牌也不在任何可枚举的语音库里。也就是说它是讲述人私有的通道，
任何第三方进程都拿不到——不是接口选择问题，而是被刻意封闭的。模组会检测到这类语音
并在配置界面提示，但不会把它列进音色列表（避免选了没声音）。

> **在线音色是同一批神经语音的云端版本**：`zh-CN-XiaoxiaoNeural` 与讲述人里的 Xiaoxiao
> 音质同源，只是必须在云端合成。若坚持完全离线，就只能用 OneCore / SAPI5 那五个音色。
>
> 如果以后用第三方工具（如 NaturalVoiceSAPIAdapter）把讲述人语音“转注册”成 SAPI 音色，
> 本模组的 SAPI 引擎会自动把它们列出来——不需要改代码。该工具属于非官方 hack
> （会读取系统文件里的密钥，可能被杀毒软件误报，也可能随 Windows 更新失效），请自行评估。

## 已知限制

- 需要 Windows 10 及以上；其他平台自动回退原版讲述人。
- 每条朗读都会先做一次本地合成，因此比原版 SAPI 直读略有延迟（通常数百毫秒）。
- SAPI5 引擎的音量/语速映射到 SAPI 的 `Volume`（0–100）与 `Rate`（-10–10 对数档位），
  与 OneCore 的百分比不是逐点等价，但方向一致。
- 在线合成需要联网：首次握手约 1 秒，之后复用长连接，单条约 0.2–0.4 秒。
- 在线音色依赖 Edge 的非公开接口（含 `Sec-MS-GEC` 令牌），微软调整后可能整体失效；
  此时模组会记录日志并自动退回本地音色，不会出现静默。
- 在线音色的语速走 SSML `prosody rate`，音量在播放端调节，二者与本地引擎不完全等价。

## 配置界面：预设与渲染的分工

界面本体在库里（`smile_libbox.api.ui.ConfigScreen`），本模组只提供一份数据描述
`smile_toolb.client.config.SmileToolbConfig`，Mod Menu 那边只负责「报名」——
连 `Screen` 都不用写（工厂用 `java.lang.reflect.Proxy` 生成，见「单 jar」那一节）：

```java
// ModMenuIntegration
@Override
public ConfigScreenFactory<?> getModConfigScreenFactory() {
    return FACTORY;   // 一个 InvocationHandler，create(parent) → Ui.config(parent, spec)
}
```

`SmileToolbConfig` 里全是这种声明：

```java
page.toggle("enabled", Ui.tr("smile_toolb.config.enabled"), null,
        config.enabled, true, bool((c, v) -> c.enabled = v));
page.slider("rate", Ui.tr("smile_toolb.config.rate"), null,
        config.rate, 50, 200, 100, integer((c, v) -> c.rate = v));
page.footer(() -> Ui.tr("smile_toolb.gui.button.select_voice", currentVoiceName()),
        () -> true, SmileToolbConfig::openVoiceList);
```

分工是硬的：

| 谁 | 负责 |
| --- | --- |
| 本模组 | 有哪些页、每页有哪些行、取值范围与默认值、改动怎么落到 `tts.json`、底部动作按钮 |
| 前置库 | 页签栏、行高与滚动吸附、标签列与控件列的对齐、重置键、滚动条、原版按钮/滑块/输入框实例、输入分发 |

因此「改界面观感」只动库一处，所有依赖它的模组一起变；本模组这边跟着游戏版本走的
只有配置项的**内容**（比如 1.21.9+ 才显示的追踪条开关）。

按钮、滑块、输入框、滚动条滑块都是 `UiHost` 创建的**真正的原版 widget**
（`Button` / `AbstractSliderButton` / `EditBox`），贴图、悬停高亮、禁用态、
讲述人全由游戏负责 —— 这也是「和原版材质一致」的唯一做法。

滑块行右侧多一颗小按钮（原版按钮贴图 + 占位字形 `T` / `≡`）：点它把滑条换成数字输入框。
输入时**每一次按键都实时校验**，出错只有一行红字 tooltip，按两类模板出：

- 内容不是这条正则能接受的东西 → `不合法的字符串！仅支持{正则名}`（默认名字是「整数」，
  也可以用 `.regexFile("txt")` 变成「.txt格式文件」，或自己起个「本地文件夹」这类名字）；
- 是数字但超出 `min~max` → `不合法的数字！仅支持{min}~{max}之间的数据`。

tooltip **只在鼠标停到输入框上时出现**，合法时不弹，免得盖住正在键入的字。合法后按回车
生效；`Esc` 只丢弃这次输入、不关界面；**点界面别的地方只会失焦，输入框保持原样**，
只有回车、再点一次切换按钮（或 `Esc`）才结束输入模式。非法内容不会被写回配置：关界面
或切回滑条时按「丢弃」处理。图标目前是占位，后续要换成贴图只动库里创建按钮的地方。

选项之间可以声明依赖：某个布尔项当**前置项**，其余行 `requires(前置行)` 挂在它下面
（JSON 写 `"requires": "<前置项的 key>"`）。前置关掉时，从属行整体禁用 —— 控件是原版
灰色禁用态、标签变暗、重置键失效、正在编辑的输入框退出输入模式；鼠标悬停时 tooltip
第一行是该行说明（默认色），**最后一行红字**「要启用此项，你需要开启『xxx』」。
本模组接的联动：系统语音 → 语速 / 音量 / 单条最大字符数 / 进游戏自动开启讲述人；
保留经验条 → 高级状态条控制；保留聊天框内容 → 草稿保留时长；启用退出按键 → 退出按键列表。

界面上的提示文字全部用**原版 tooltip**（库的 `UiHost#tooltip` / `UiHost#tooltipLines` →
原版 `renderComponentTooltip` / `setComponentTooltipForNextFrame`），所以是原版黑框、
跟随鼠标、自动换行并自动翻到屏幕内侧，不再是自绘色块。两处会触发：

- **配置项说明**：鼠标停在某行的**标签文字区**，显示该行定义里的 `tooltip`；
- **数字输入**：内容非法且鼠标停在输入框上时，整条红字给一条模板化提示
  （`不合法的字符串！仅支持…` 或 `不合法的数字！仅支持 a~b 之间的数据`）；
  合法时只在切换按钮上给范围提示。

### 两种定义方式

同一份 `ConfigSpec` 有两条入口，画出来完全一样：

- **代码逐条定义**（本模组用的这种）：上面那些 `page.toggle(...)` / `page.slider(...)`，
  能直接写 lambda、动态取按钮文字、按运行时能力决定加不加行；
- **JSON 定义**（`smile_libbox.api.ui.ConfigLayout`）：适合界面固定的模组，页面与行写成
  资源文件，值通过 `ConfigValues` 接口映射到自己的配置文件。

```java
ConfigSpec spec = ConfigLayout.load("mymod/config_gui.json", parent, myValues, actions);
```

```json

  "pages": [{
    "title": "mymod.gui.tab.general",
    "rows": [
      { "type": "toggle", "key": "enabled", "label": "mymod.config.enabled", "default": true },
```

## 配置界面布局算式

库里的排版参数照 masa 系界面的比例定的，改之前先看一眼：

| 量 | 取值 | 依据 |
| --- | --- | --- |
| 标签列宽 | 全部页里最宽的那条标签 | 按当前页算会让两页一宽一窄，切页时整张表左右边界一起跳 |
| 控件宽上限 | **206** | 超过之后整行被拉得过长，滑条在宽屏上又细又长 |
| 控件宽下限 | 120 | 再窄滑条拖不动、开关上的字也放不下 |
| 右端留白 | `24 × 3 / GUI缩放`，限幅 8~40，且不小于 `4+8+6` | 逻辑像素随缩放变化，固定值在大缩放下一挤就压到滚动条 |
| 列表右侧内缩 | 4 | 让滚动条更贴右缘；RESET 右边界固定为 `宽度 − 留白`，并与滚动条保持 ≥ 6 px |
| **可见行数** | `min(ceil(可视区高 / 22), floor(可视区高 / 20))` | 向上取整比旧的 floor 多显示一行；同时保证每行至少塞得下 20px 控件 |
| **实际行高** | `可视区高 / 可见行数`，上下留白 `(行高 − 20) / 2` | 行高整除可见区，最后一行不会只露半截；两页共用同一套行高 |
| **滚动步长** | 整行 | `scroll` 存的是「卷起行数」而非像素，滚轮一次 2 行，拖/点滚动条也吸附到整行 |
| **滚动条** | 暗色轨道（背景） + 原版按钮做的滑块（前景） | 两层结构跟 masa 系一致；滑块用真 widget 省掉各版本差异极大的 `blitSprite` 签名 |

排版顺序固定为「标签列 + 10 + 控件 + 2 + RESET」。滑块行的控件区再留 18px 给切换小按钮。
控件封顶后多出来的横向空间由标签列吸收，整行仍收在右端锚点上，不会在控件和 RESET 之间留洞。

举例：427×240、缩放 3 时可视区 148px → 7 行 × 21px = 147px，正好铺满；
原来 `floor(148/22)=6` 行之外还会露出第 7 行的半截，现在这行完整显示。

两页共用同一套标签列、控件宽度、行高与可见行数，所以切页时只有行内容变、
列的边界和滚动条都不动。

## 单 jar 与 Stonecutter（回归检查）

**发布物只有一个** `build/libs/smile_toolb-1.0.4.jar`，`depends.minecraft` 写
`>=1.20.1`，1.20.1 ~ 26.2 共用同一份字节码。能做到这一点，是因为模组侧**零
`net.minecraft` 引用**：

| 原本会带 MC 类型的地方 | 现在怎么绕开 |
| --- | --- |
| 配置界面 | 只产 `ConfigSpec`，渲染交给库的 `ConfigScreen`（按版本编译在库里） |
| 讲述人 | `SystemNarrator extends VersionedNarrator`，实现的是库定义的 `onSay/clear/active/destroy` 钩子，接口适配在库里 |
| 输入事件 / 状态条 / 聊天草稿 | 全部走库的 mixin 与 `Ui` 门面 |
| Mod Menu 入口 | `ConfigScreenFactory.create(Screen)` 的 `Screen` 用 `java.lang.reflect.Proxy` 接住（见 `ModMenuIntegration` 注释） |
| 两个 mixin | 目标是 `com.mojang.text2speech.Narrator` 与第三方 `LocatorBarRenderer`，都不是 `net.minecraft.*`，名字跨版本不变 |

Stonecutter 只保留**两个节点**，产物**不发布**，用途是**两端夹逼的回归检查**：
谁往源码里塞了 MC 引用，那个节点会当场编译失败。

| 节点 | 角色 | 编译目标 | Mod Menu（仅编译期） |
| --- | --- | --- | --- |
| 1.20.1 | 基准，产物从这里取 | Java 17（class major 61） | 7.2.2 |
| 1.21.11 | 最新 intermediary，夹逼的另一头 | Java 21 | 17.0.1 |

中间 6 个版本（1.20.4 / 1.20.6 / 1.21.1 / 1.21.4 / 1.21.5 / 1.21.8）的
`gradle.properties` 归档在 `archived-versions/`。要加回来只需拷到 `versions/<版本>/`
再写进 `settings.gradle` 的 `versions` 行——它们当初编出来的字节码与本 jar 逐字节相同，
删掉不影响通用性。

```bash
./gradlew build               # 2 个节点（回归检查）
python tools/build_release.py # 收敛成 build/libs/smile_toolb-<版本>.jar
./gradlew :1.20.1:runClient   # 起开发客户端
```

`build_release.py` 以 **1.20.1 节点**为基准（Java 17 编译，class major 61，17/21/25
的运行时都能加载），并做两件事：

1. 把 1.21.11 节点的 class 抹掉 class 版本号后逐字节比对 —— 只要有一个类不同，
   就说明有代码按版本分叉了，「一个 jar」的前提被破坏，脚本直接报错；
2. 校验产物内零 `net/minecraft` 引用、`minecraft` 范围为 `>=1.20.1`、`depends` 无 `malilib`。

`fabric.mod.json` 里 `minecraft` / `java` 现在是固定值（`>=1.20.1` / `>=17`），
不再按节点替换；各节点的 MC / Fabric API / Mod Menu / 库坐标仍集中在
`versions/<版本>/gradle.properties`。

**Mod Menu 是可选依赖**：用 `modCompileOnly` + `modLocalRuntime` 引入，只写进
`suggests` 而不是 `depends`，没装时 Loader 不会解析那个 entrypoint。

### 26.2 为什么一个 jar 就能跑

26.x 起 Mojang 不再提供 intermediary，游戏 jar 里直接是 `net.minecraft.client.*` 官方名；
按 1.20.1 编译的 class 常量池里若是 `net/minecraft/class_437`，两者不能混用。

改造后模组侧一个 `net.minecraft` 描述符都没有（`build_release.py` 每次都会校验），
因此同一份 class 在 intermediary 与 named 两代上都能直接用；真正按命名空间分叉的
代码（`VersionedScreen` / `UiBackend` / `VersionedNarrator` / 三个注入点）全在前置库里，
由库的 `tools/build_named26.py` 单独出 `smile_libbox-1.0.4+26.2.jar`。

换句话说：**版本分叉集中在库，使用方回到一个 jar**——这也正是把配置界面预设化
想要的最终形态。

### 预设定义要点

| 位置 | 处理 | 为什么 |
| --- | --- | --- |
| `SmileToolbConfig.miscPage()` | 追踪条两个开关由 `BarFeatureDetector.get().present()` 决定加不加 | 1.20.x 没有追踪条，显示出来只会让人以为坏了；用运行时探测而不是编译期版本条件，因为 VanillaBackport 会改变能力 |
| `page.footer(...)` | 传 `Supplier<String>` 而不是字符串 | 音色名、假人数量是运行时才知道的；库每帧都会重新取一次标签，假人数量因此能跟着在线名单实时变 |
| `commit()` | 每次改动立即 `SmileConfig.save()` + `TtsEngine.applyConfig()` | 与原来 `onConfigsChanged` 同频：改完立刻能听到效果，不必点「完成」 |
| `ExitKeyScreen` | 自己实现 `UiScreen` | 退出按键是键名列表而不是单个值，得有自己的列表页 |
| 标题与标签 | 全部 `Ui.tr(...)`，构建 spec 时才翻译 | 界面可能在资源包加载完之前被 Mod Menu 取工厂时构造，早翻会定格成键名 |

### 版本适配点（现在由库承担）

| 分界 | 变化 | 库里的处理位置 |
| --- | --- | --- |
| 1.20.2 | `mouseScrolled` 增加水平分量、`renderBackground` 增加窗口参数 | `VersionedScreen` |
| 1.21 | `new ResourceLocation(..)` 弃用 | 本模组已删除无人使用的 `SmileSToolb.id()` |

| 1.21.9 | 键盘/鼠标回调改为事件对象、窗口句柄改名、键位分类对象化 | `LibScreenKeyMixin` / `LibMouseMixin` / `VersionedScreen` / `McCalls.keyMapping` |
| 1.21.9 | 快捷栏上方改为上下文条（经验条 / 追踪条 / 跳跃条） | `LibContextualBarMixin` + 本模组 `ContextualBarController`（状态条控制） |

## 前置库 Smile's Lib Box

本模组把跨版本兼容层拆到了独立前置模组 **`Smile's Lib Box`**（`smile_libbox`）。
它**按游戏版本出 9 个 jar**（8 个 Stonecutter/Loom 节点 + 1 个 26.2 官方名 jar，
另有 `+generic.jar` 兜底）：`smile_libbox.api` / `api.ui` 下不引用任何 Minecraft 类，
所以版本判断与 UI 契约在所有版本通用；`smile_libbox.client.compat` / `mixin` 下的
适配类与该版本 MC 一起编译，由对应的 jar 提供正确的签名（intermediary 代还带 refmap）。

- 运行期版本判断在 `smile_libbox.api.GameVersion`；游戏 / 数据包 / 资源包版本由
  `MinecraftVersions` 提供固定接口（读取客户端 jar 的 `version.json`，把 1.21.9
  前后两套 `pack_version` 结构统一成主版本 + 次版本）。
- 适配层：`VersionedScreen`、`UiBackend`、`McCalls`、`VersionedNarrator`，以及
  `LibScreenKeyMixin` / `LibMouseMixin` / `LibContextualBarMixin`。26.2 的适配层在
  `named26/src`，由 `tools/build_named26.py` 用官方名直接 javac 编译。
- 本模组只依赖 `smile_libbox.api.ui.Ui` 门面、`ConfigSpec` / `ConfigScreen` 界面预设与
  `InputEvents` / `BarEvents` 两个零 MC 引用的事件总线。这部分在所有版本通用，所以 TTS 引擎、
  音频子进程、配置读写、假人、状态条控制、配置界面这些核心代码只写一份。
- 依赖方式：`modImplementation "smile_libbox:smile_libbox:1.0.4"`（库先执行
  `./gradlew build publishToMavenLocal`），`fabric.mod.json` 里声明
  `"depends": { "smile_libbox": "*" }`。运行时把**与目标游戏版本一致的那个库 jar**
  放进 `mods/`；版本 jar 声明 `minecraft: ~<版本>`，装错会被 Loader 拒绝。
- **26.2**：库的 `+26.2.jar` 自带四个按官方名写描述符的 client mixin（自定义退出按键、
  上下文条接管、界面/全局鼠标输入、聊天框草稿）；本模组的 26.2 包由
  `tools/build_named26.py` 生成，做法见上一节。

### 怎么判断版本（给其他模组作者）

依赖本库的模组判断版本有四种依据，按需要选：

| 想判断什么 | 用哪个接口 |
| --- | --- |
| 游戏版本区间 | `GameVersion.atLeast("1.21.9")` / `Conditional.matches(">=1.21.9")` |
| 数据包 / 资源包格式版本 | `MinecraftVersions.dataPackAtLeast(15, 0)`、`resourcePackAtLeast(75, 0)`、`Conditional.matches("datapack:>=15.0")` |
| 协议 / 世界 / Java 版本 | `MinecraftVersions.protocol()`、`world()`、`java()`、`summary()` |
| ABI 能力 / 模组 / 类是否存在 | `Compat.eventBasedInput()` 等固定布尔、`cap:`、`mod:`、`class:` 表达式 |

然后把版本相关实现拆成独立类，用字符串类名装配：

```java
BarHooks hooks = Conditional.choose(BarHooks.class,
        ">=1.21.9 => mymod.compat.v1219.ModernBarHooks",
        "*        => mymod.compat.legacy.LegacyBarHooks");
```

字符串类名不产生符号引用，条件不成立的那些类永远不会被加载，所以所有实现可以一起
打进同一个 jar。Mixin 侧继承 `smile_libbox.api.VersionedMixinPlugin` 自己写门控规则。

**但「拆类 + 延迟加载」这条路径只在同一个命名空间代内成立。** 26.x 起 Mojang 改用
官方类名（`net/minecraft/client/KeyMapping`），启动日志出现 `Mappings not present!`，
而按 1.20.1 编译的 class 常量池里是 `net/minecraft/class_304` 这类 intermediary 名。
类名是编译期写死的，延迟加载、反射都改不了。

本模组走的是**另一条路**：把 MC 类型全部隔离进库按代编译的适配层，
主 jar 只依赖 `smile_libbox.api.ui` 纯 Java 门面、常量池零 `net/minecraft` 引用，
从而用单个 jar 同时进 1.20.1 与 26.2。改造中途用 `+generic.jar` 时曾崩在
`McCalls.keyMapping` → `NoClassDefFoundError: net/minecraft/class_304`，
正是没做完这层隔离时的表现。

**配置界面预设化之后这条路又通了**：界面不再继承 `Screen`，主 jar 里除
`ModMenuIntegration` 那个带 `Screen` 参数的工厂方法之外，常量池没有一个
`net/minecraft` 描述符。按版本出 jar 仍是必要的（mixin 与版本门控要对着具体签名编译），
但各份 jar 之间只差那几个类 —— 26.2 的包因此可以复用 1.20.1 的全部产物。
完整结论见 [`VERIFY.md`](VERIFY.md) 第 0 节与
[`Smile's Lib Box/README.md`](../Smile's%20Lib%20Box/README.md)。

## 构建

先构建并发布前置库，再构建本模组（Gradle 配置期会解析依赖坐标）：

```bash
cd "../Smile's Lib Box" && ./gradlew build publishToMavenLocal
cd "../Smile's toolb" && ./gradlew build          # 2 个节点（回归检查）
cd "../Smile's toolb" && python tools/build_release.py   # 收敛成一个 jar
```

本机需要 JDK 21+ 就能构建本模组（两个节点分别按 17 / 21 编译）；
只有前置库的 26.2 包另需 JDK 26 的 `javac`。Mod Menu 由 Loom 从
Modrinth / Terraformers 仓库拉取，不需要手动准备。
只想跑一个版本时用 `./gradlew :1.20.1:runClient`。

需要实机核对界面时，加自检开关让开发客户端启动后自动打开一次配置界面，读日志里的
`配置界面自检` 行（页签数 / 每页行数 / 追踪条开关是否显示）：

```bash
./gradlew :1.20.1:runClient -Dsmile_toolb.selftest.open_config=true
```

正式整合包里改用 JVM 参数 `-Dsmile_toolb.selftest.open_config=true` 或环境变量
`SMILE_TOOLB_SELFTEST_OPEN_CONFIG=1`；默认关闭，正常游玩不会弹界面。
